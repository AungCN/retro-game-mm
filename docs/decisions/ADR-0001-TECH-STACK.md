# ADR-0001: Web Application Technology Stack

- Status: PROPOSED — owner decision required
- Date: To be completed
- Decision owner: To be completed

## Context

The project needs a maintainable browser-first application with a catalogue UI, native 2D game modules, a generic PS1 BYOR player through WebAssembly emulator cores (SCR-001), offline support, automated testing, and a later mobile packaging option.

The emulator adapters add constraints the original stack did not have:

- The app must be cross-origin isolated (COOP/COEP) in development, preview, production, and when served offline by the service worker (`docs/quality/SECURITY_GUIDELINES.md`).
- Emulator cores are GPL-licensed third-party binaries that must be pinned, self-hosted, and kept as separate files.
- The host must serve custom headers on every static file, including `.wasm` and worker scripts.

## Candidate approach

- TypeScript as the primary language
- React for platform UI
- Vite as development/build tooling, with COOP/COEP/CORP set in both `server.headers` and `preview.headers`
- Native game runtime: **open** — Canvas 2D vs. Phaser is decided in Phase 03 planning (owner decision O-5); no spike in Phase 01
- Emulator adapters per ADR-0002 (EmulatorJS-based `wasm-libretro` candidate, validated in SPIKE-001)
- IndexedDB for structured local data; OPFS / File System Access per ADR-0003
- Service Worker + Cache Storage for offline assets (hand-written or a library chosen in Phase 05)
- Vitest and Playwright for testing
- Capacitor to evaluate during the mobile phase

- **Unpinned dependencies:** `@emulatorjs/emulatorjs` declares an optional dependency on `@emulatorjs/cores@latest` (every core, unpinned, some with non-commercial licences) plus build-tool dependencies, and `core-pcsx_rearmed` depends on `@emulatorjs/emulatorjs@latest`. ## Hosting requirements and comparison

Requirements: custom response headers on **every** static file (HTML, JS, workers, `.wasm`); `application/wasm` MIME type; per-file size limit above the largest core file; HTTPS; static hosting only (no server functions needed). Disc images are never hosted.

| Option | Custom headers | Per-file limit | Notes |
|---|---|---|---|
| Cloudflare Pages | `_headers` file; up to 100 rules, 2,000 characters per line | 25 MiB per asset | 20,000 files per site on the Free plan. Headers from `_headers` do not apply to responses generated by Pages Functions/Worker code — not used here. |
| Netlify | `_headers` file or `netlify.toml`; apply to files Netlify serves from its own store | Not confirmed from current docs | `_headers` rules are global, not per deploy context. Community reports of COOP/COEP not taking effect in some setups — must be verified on a preview deploy. |
| Self-hosted (Caddy or nginx) | Full control | None beyond the server | Highest operational effort (TLS, updates, uptime). |
| GitHub Pages | Not supported | — | Excluded. A service-worker workaround (`coi-serviceworker`) is rejected: it reloads the page and makes isolation depend on a script. |

**Recommendation:** Cloudflare Pages, subject to a header check on a preview deploy before the first public release. It has documented header support with known limits, and a 25 MiB per-file limit comfortably above PS1 core sizes (the npm core package is about 4 MB unpacked). Self-hosting stays the fallback if a provider check fails. The host is selected by the owner in this ADR; no deployment happens in Phase 01.

## Licence direction

- Repository licence direction: **GPL-3.0-or-later** (owner decision D1). The LICENSE file (verbatim GNU GPL-3.0 text) is a separately approved item.
- MIT and Apache-2.0 dependencies are compatible with GPL-3.0-or-later.
- Emulator cores keep their own licences and are shipped as separate files with their licence texts and a source offer.
- The GPL-2.0 status of the PS1 core (table above) is an open licence question. It does not block development or the spike, but must be resolved before public distribution. This is not legal advice.

## Alternatives to compare

- Vue or another UI framework instead of React
- Plain TypeScript/Canvas instead of a game engine (deferred to Phase 03)
- Another maintained browser game engine instead of Phaser (deferred to Phase 03)
- A different PWA/service-worker integration (Phase 05)
- Building the PS1 core from source with Emscripten instead of using the EmulatorJS build (heavier toolchain; reconsider if SPIKE-001 shows EmulatorJS cannot meet streaming or CSP needs)

## Evaluation criteria

- Browser and mobile-browser support
- Cross-origin isolation in every environment, including offline
- Offline and asset-loading behavior
- TypeScript support and developer experience
- Rendering performance for target games
- Bundle size and load time
- Accessibility integration for the platform shell
- Maintenance/community health and documentation
- License compatibility with GPL-3.0-or-later
- Ease of testing and future mobile packaging

## Recommendation

- Use React + TypeScript + Vite for the platform UI, with identical COOP/COEP/CORP headers in `server.headers` and `preview.headers`. SPIKE-001 A1 records whether this works as configured.
- Leave the native game runtime open until Phase 03 planning.
- Recommend Cloudflare Pages as the host, with a preview-deploy header check.
- Resolve the PS1 core licence question before public distribution.

## Consequences

- Hosting is limited to providers with per-file custom headers; GitHub Pages is out.
- Every third-party asset must be self-hosted, because COEP blocks cross-origin resources.
- Tests must assert `crossOriginIsolated` in dev, preview, and offline modes.
- Adding the GPL-3.0 LICENSE file and resolving core licence compatibility are prerequisites for public distribution.
